# userland/ — provenance and packaging

What ships as the device-side shell for the harness, where it came from, and how it is deployed.
Verified by the orchestrator; see `../planning/ENVIRONMENT.md`.

## Contents

| File | What |
|---|---|
| `busybox` | Alpine `busybox-static` 1.37.0-r14, `aarch64`, ELF 64-bit LSB executable, statically linked (1,115,944 bytes) |
| `rm.sh` | The `rm` → trash shim, deployed with `@SHELL@` substituted (ADR-004 §5) |
| `SHA256SUMS` | `sha256sum` of `busybox`, regenerated by `scripts/fetch-userland.sh` |
| `.PKGINFO`, `.SIGN.RSA.alpine-devel@…` | The Alpine package metadata and its signature, kept for provenance |
| `../../app/src/main/assets/userland/busybox` | The same bytes, which is what actually reaches the device |

## Source

```
https://dl-cdn.alpinelinux.org/alpine/v3.21/main/aarch64/busybox-static-1.37.0-r14.apk
```

An `.apk` is a `.tar.gz`; the binary is the member `bin/busybox.static`. The package metadata in
`.PKGINFO` reports `pkgname = busybox-static`, `pkgver = 1.37.0-r14`, `arch = aarch64`,
`license = GPL-2.0-only`, `datahash = 8f53f0dd…` — the file we ship hashes to the value in
`SHA256SUMS`, and the signature member is present and was carried along.

A first attempt at `alpine/v3.20/main/aarch64/busybox-static-1.36.1-r2.apk` returned a 404 from the
mirror. That is recorded because the substitution must be visible: the version shipped is the one
that was actually downloaded and hashed, not the one first guessed.

## Licence

**GPL-2.0-only.** This is the one non-MIT artefact in the project. Bundling busybox in a distributed
APK imports GPL obligations (source availability, licence text, no added restrictions). For a
private, sideloaded PoC that is fine; for anything distributed, this file is the trigger to revisit.
Not a constraint on the harness code, which stays MIT.

## Deployment on the device

Two paths are possible; the app tries (1) and the probe in `planning/PLAN.md` W0.3 records which one
the platform actually permits.

1. **Assets → app storage (primary).** With `targetSdk 28` (ADR-005 §8) the app keeps execute
   permission for its own data directory, so the binary is unpacked from
   `assets/userland/busybox` to `files/userland/busybox`, `chmod 700`, and exec'd there. This is how
   Termux itself survives Android 10's W^X change, and it needs nothing from the build system.
2. **Native library dir (fallback).** Ship the same file as `jniLibs/arm64-v8a/libbusybox.so` with
   `extractNativeLibs="true"`; exec from `/data/app/.../lib/arm64/` is permitted even on modern
   targets. The trade: the file appears in the APK's native section and is abi-filtered.

`rm.sh` is deployed next to the shell with its `@SHELL@` placeholder replaced, and the tool layer
puts its directory first on `PATH` ahead of the busybox applet directory.

## ABI note

`arm64-v8a` only. The API-36 `x86_64` emulator used for development runs it anyway through NDK
translation (`ro.enable.native.bridge.exec=1`, `libndk_translation.so` present) — verified by running
this binary on it and getting `HELLO_ARM64`, an interactive `sh`, and working applet symlinks.
